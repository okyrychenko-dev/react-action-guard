# Gate ecosystem and commercial expansion on consumer evidence

Accepted on 2026-10-12 for ticket 29. Retain independently composable Core, UI, Router, Query and Devtools packages. Defer new adapters and commercial services until a concrete integration demonstrates recurring coordination work and measurable value; reviewer enthusiasm is not adoption evidence.

## Evidence boundary

Existing [Query guidance](../../packages/docs/src/guides/mutations.md) and [Router guidance](../../packages/docs/src/guides/navigation.md) document implemented integrations, mutation lifetime, confirmation and Next limitations. The [showcase](../../examples/enterprise-demo/README.md) composes real public libraries around simulated application operations. The [pilot plan](../../packages/docs/src/learning/workflow-pilot.md) explicitly leaves real application measurement external. These support retaining existing integrations; they do not establish demand or reliability rankings for new libraries. Current release verification remains ticket 30, independent of these decisions.

## Lightweight demand capture

Use the existing local issue tracker for a consumer report: workflow and participating owners, producers/consumers/scopes, current public API composition, repeated wiring or diagnostic failure, reproducible example, before/candidate measurements, native behavior to preserve, cleanup/SSR/peer constraints and named evaluator. Remove sensitive data before retaining reports. External accounts, dashboards and telemetry collection are unnecessary to gather this evidence.

Count repeated occurrences in actual integrations rather than counting review mentions. One runnable consumer can justify an investigation; a maintained adapter needs recurring demonstrated pain and a credible maintenance owner. Record unknown measurements as unknown, with the evidence source and date. The pilot's scenario/measurement matrix is the starting point, not a completed production result.

Every adopted proposal needs a separate bounded specification, public testing seam, demonstrable boilerplate/value reduction, compatibility and cleanup checks, and release/maintenance ownership. New siblings must not become required dependencies of unrelated packages. No new adapter, service or runtime follow-up is accepted by this register; documentation of the current composition path is retained.
